# 列表

{{ video_embed | replace("%%VID%%", "x8oLIEtSRBs")}}

OCaml 列表是一系列类型相同的值，以单链表实现。列表在 OCaml 中是一等公民：语言提供了创建和使用列表的专门语法支持。这是 OCaml 与许多其他函数式语言共有的特性。像 Python 这样的主流命令式语言如今也提供了类似支持。程序员往往更喜欢把列表当作语言的一等组成部分直接使用，而不是通过库来操作它们（像 C 和 Java 那样）。

## 构建列表

{{ video_embed | replace("%%VID%%", "I9u4kFPM7YI")}}

**语法。** 构建列表有三种语法形式：
```ocaml
[]
e1 :: e2
[e1; e2; ...; en]
```
空列表写作 `[]`，读作"nil"，这个名字源自 Lisp。给定一个列表 `lst` 和元素 `elt`，我们可以把 `elt` 加到 `lst` 的前面，写作 `elt :: lst`。双冒号运算符读作"cons"，这个名字也来自 Lisp，指的是一个 <u>cons</u>tructs（构造）内存中对象的运算符。"Cons"也可以用作动词，比如"我会把一个元素 cons 到列表上"。列表的第一个元素通常称为它的*头部*（head），其余元素（如果有的话）称为它的*尾部*（tail）。

cons 运算符 `::` 是右结合的，这意味着 `e1 :: e2 :: e3` 
被理解为 `e1 :: (e2 :: e3)`，而不是 `(e1 :: e2) :: e3`。

方括号语法很方便，但并不是必需的。任意列表
`[e1; e2; ...; en]` 都可以用更原始的 nil 和 cons 语法表示：
`e1 :: e2 :: ... :: en :: []`。当一种好用的语法可以用语言中更原始的语法定义出来时，我们称这种好用的语法为*语法糖*（syntactic sugar）：它让语言变得更"甜"。把语法糖转换为更原始的语法，称为"去糖"（desugaring）。

因为列表的元素可以是任意表达式，所以列表可以是
嵌套的深度任意深，例如 `[[[]]; [[1; 2; 3]]]`。

**动态语义。**

- `[]` 本身已经是一个值。
- 如果 `e1` 计算得到 `v1`，且 `e2` 计算得到 `v2`，那么 `e1 :: e2` 计算得到 `v1 :: v2`。

由这些规则以及方括号语法如何去糖化，我们得到以下推导规则：

- 如果对所有 `i` ∈ `1..n` 都有 `ei` 计算得到 `vi`，那么 `[e1; ...; en]` 计算得到 `[v1; ...; vn]`。

在求值规则中反复写"求值为"逐渐显得啰嗦。让我们引入一个更简洁的记号：用 `e ==> v` 表示"e 求值为 v"。注意 `==>` 不是 OCaml 语法的一部分，而是我们用来描述语言的元语言符号。用这个记号，上面后两条规则可以改写为：

- 如果 `e1 ==> v1` 且 `e2 ==> v2`，那么 `e1 :: e2 ==> v1 :: v2`。
- 如果对所有 `i` ∈ `1..n` 都有 `ei ==> vi`，那么 `[e1; ...; en] ==> [v1; ...; vn]`。

**静态语义。**

列表的所有元素必须具有相同的类型。如果元素类型是 `t`，那么列表的类型就是 `t list`。你应该从右到左读这样的类型：`t list` 是一个 `t` 的列表，`t list list` 是一个 `t` 的列表的列表，等等。这里的 `list` 本身不是一个类型：没有办法构造一个仅为 `list` 类型的 OCaml 值。相反，`list` 是一个*类型构造器*：给定一个类型，它产生一个新的类型。例如，给定 `int`，它产生类型 `int list`。你可以把类型构造器想象成作用于类型而非值的函数。

类型检查规则：

- `[] : 'a list`
- 如果 `e1 : t` 且 `e2 : t list`，那么 `e1 :: e2 : t list`（若对优先级困惑，后者表示 `(e1 :: e2) : t list`）。

在 `[]` 的规则中，记住 `'a` 是一个类型变量：它代表一个未知的类型。所以空列表是一个元素类型未知的列表。如果我们在它前面 cons 一个 `int`，比如 `2 :: []`，编译器就会推断出这个特定列表的 `'a` 必须是 `int`。但如果在另一个地方我们在它前面 cons 一个 `bool`，比如 `true :: []`，编译器会推断出这个特定列表的 `'a` 必须是 `bool`。

实际上，构造列表只有两种方法：nil 和 cons。所以如果我们想把列表分解成它的组成部分，就必须说明两种情况：列表为空时做什么，以及列表非空时（即，一个元素 cons 到另一个列表上时）做什么。我们用一种叫*模式匹配*的语言特性来实现这一点。

下面是使用模式匹配计算列表总和的示例：
```{code-cell} ocaml
let rec sum lst =
  match lst with
  | [] -> 0
  | h :: t -> h + sum t
```

这个函数会取得输入 `lst`，并检查它是否具有与空列表相同的形状。
如果是，就返回 0。否则，如果它匹配列表形状 `h :: t`，
就让 `h` 成为 `lst` 的第一个元素，让 `t` 成为 `lst` 的其余元素，
并返回 `h + sum t`。这里的变量名表示"头部"和"尾部"，
是一种常见习惯；当然，如果愿意，我们也可以使用其他名字。
另一种常见习惯是：
```{code-cell} ocaml
let rec sum xs =
  match xs with
  | [] -> 0
  | x :: xs' -> x + sum xs'
```
也就是说，输入列表命名为 xs（读作 EX-uhs），头元素命名为
x，尾部命名为 xs'（读作 EX-uhs prime）。

从语法上讲，没有必要使用这么多行来定义 `sum`。我们可以
全部在一行完成：
```{code-cell} ocaml
let rec sum xs = match xs with | [] -> 0 | x :: xs' -> x + sum xs'
```
或者，请注意 `with` 之后的第一个 `|` 是可选的，无论有多少个
我们使用的行，我们也可以写：
```{code-cell} ocaml
let rec sum xs = match xs with [] -> 0 | x :: xs' -> x + sum xs'
```
多行格式是本书中我们通常使用的格式，因为它让人眼更容易看清语法结构。不过，OCaml 代码格式化工具在代码足够短、能放进一行时，往往会将其整理为单行格式。

这是使用模式匹配计算列表长度的另一个示例：
```{code-cell} ocaml
let rec length lst =
  match lst with
  | [] -> 0
  | h :: t -> 1 + length t
```
请注意我们实际上并不需要变量 `h` 在右侧
模式匹配。当我们想要指示模式中存在某些值时
无需实际命名，我们可以编写 `_` （下划线字符）：
```{code-cell} ocaml
let rec length lst =
  match lst with
  | [] -> 0
  | _ :: t -> 1 + length t
```
这个函数实际上已经内置在 OCaml 标准库的 `List` 模块中，名字叫 `List.length`。这里的"点"表示法表示模块 `List` 中名为 `length` 的函数，与许多其他语言中的点号用法类似。

这是第三个示例，它将一个列表附加到
另一个列表：
```{code-cell} ocaml
let rec append lst1 lst2 =
  match lst1 with
  | [] -> lst2
  | h :: t -> h :: append t lst2
```
例如，`append [1; 2] [3; 4]` 的结果是 `[1; 2; 3; 4]`。这个函数实际上就是内置运算符 `@`，所以我们可以直接写 `[1; 2] @ [3; 4]`。

{{ video_embed | replace("%%VID%%", "VDRTatjSl0E")}}

作为最后一个例子，我们可以编写一个函数来确定是否
列表为空：
```{code-cell} ocaml
let empty lst =
  match lst with
  | [] -> true
  | h :: t -> false
```
但是有一种更好的方法可以在不进行模式匹配的情况下编写相同的函数：
```{code-cell} ocaml
let empty lst =
  lst = []
```

注意上面所有这些递归函数与自然数归纳法证明之间的相似性：每个自然数要么是 0，要么是比另一个自然数 $n$ 大 1，因此归纳证明包含 0 的基本情况和 $n + 1$ 的归纳情况。同样，我们上面所有函数都包含一个处理空列表的基本情况，以及一个处理"比另一个列表多一个元素"的递归情况。这种相似性并非巧合。归纳与递归之间存在着深刻的联系；本书后面会更详细地探讨这一关系。

顺便一提，标准库提供了两个函数 `List.hd` 和 `List.tl`，分别返回列表的头部和尾部。但在惯用 OCaml 代码中，不建议直接对列表使用这两个函数。问题在于，如果对空列表调用它们，会抛出异常，而你必须记得处理这个异常。更好的做法是使用模式匹配：这样编译器会强制你至少处理空列表和非空列表两种情况，从而避免异常，让程序更健壮。

## （不）改变列表

列表是不可变的。没有办法把列表中的某个元素
改成另一个值。相反，OCaml 程序员会从旧列表创建新列表。
例如，假设我们想编写一个返回相同列表的函数
作为其输入列表，但把第一个元素（如果有）加一。
我们可以这样做：
```ocaml
let inc_first lst =
  match lst with
  | [] -> []
  | h :: t -> h + 1 :: t
```

现在你可能会担心这样做是否浪费空间。毕竟，编译器至少有两种方式来实现上面的代码：

1. 在模式匹配到 cons 时，把整个尾部列表 `t` 复制一份来创建新列表，导致内存使用量与 `t` 的长度成正比地增加。

2. 在旧列表和新列表之间共享尾部列表 `t`，这样内存使用量几乎不会增加——只需要额外的一块内存来存储 `h + 1`。

事实上，编译器实现的是后者。所以不必担心。编译器之所以能安全地实现共享，正是因为列表元素是不可变的。如果它们可变，我们就不得不担心"我的列表是否与你的列表共享"以及"我所做的改动会不会体现在你的列表里"。因此，不可变性既让代码更容易推理，也让编译器可以安全地执行这类优化。

## 与列表的模式匹配

我们在上面看到了如何使用模式匹配来访问列表。让我们更仔细地
观察这个语言特性。

**语法。**
```ocaml
match e with
| p1 -> e1
| p2 -> e2
| ...
| pn -> en
```

每个子句 `pi -> ei` 称为模式匹配的*分支*或*情况*。
整个模式匹配中的第一个竖线是可选的。

这里的 `p` 是一种新的语法形式，称为*模式*。目前，有一个模式
可能是：

* 变量名称，例如 `x`
* 下划线字符 `_`，称为 *通配符*
* 空列表 `[]`
* `p1 :: p2`
* `[p1; ...; pn]`

变量名称在模式中不得出现多次。例如，
模式 `x :: x` 是非法的。通配符可以出现任意多次。

随着我们更多地了解 OCaml 中可用的数据结构，我们将扩展
模式的可能性。

**动态语义。**

{{ video_embed | replace("%%VID%%", "sz72NP4u4DQ")}}

模式匹配涉及两个相互关联的任务：判断某个模式是否匹配某个值，以及确定该值的哪些部分应当与模式中的变量名绑定。前一个任务直观上是在判断模式与值是否具有相同的*形状*（shape）。后一个任务则是确定模式引入了哪些*变量绑定*（variable binding）。例如，考虑下面的代码：
```{code-cell} ocaml
match 1 :: [] with
| [] -> false
| h :: t -> h >= 1 && List.length t = 0
```
在求值第二个分支的右侧时，`h` 绑定到 `1`，`t` 绑定到 `[]`。我们用 `h->1` 来表示变量绑定：即 `h` 具有值 `1`；这不是 OCaml 语法，而是我们用来推理语言的一种记号。因此，第二个分支产生的变量绑定是 `h->1, t->[]`。

使用这种记号，下面给出模式何时匹配某个值以及匹配后产生哪些绑定的定义：

* 模式 `x` 匹配任何值 `v`，并产生变量绑定 `x->v`。

* 模式 `_` 匹配任何值，不产生任何绑定。

* 模式 `[]` 匹配值 `[]`，不产生任何绑定。

* 如果 `p1` 匹配 `v1` 并产生绑定集 $b_1$，且 `p2` 匹配 `v2` 并产生绑定集 $b_2$，那么 `p1 :: p2` 匹配 `v1 :: v2`，并产生绑定集 $b_1 \cup b_2$。注意 `v2` 必须是一个列表（因为它位于 `::` 的右侧），且可以是任意长度：0 个、1 个或多个元素。另外注意，$b_1 \cup b_2$ 的并集永远不会出现同一变量被重复绑定的问题，因为语法限制变量名不能在模式中多次出现。

* 如果对所有 `i` ∈ `1..n`，`pi` 匹配 `vi` 并产生绑定集 $b_i$，那么 `[p1; ...; pn]` 匹配 `[v1; ...; vn]`，并产生绑定集 $\bigcup_i b_i$。注意这个模式精确指定了列表的长度。

现在我们可以说明 `match e with p1 -> e1 | ... | pn -> en` 的求值方式：

* 将 `e` 求值为值 `v`。

* 按模式在匹配表达式中出现的顺序，依次尝试将 `v` 与 `p1`、`p2`……进行匹配。

* 如果 `v` 与任何模式都不匹配，求值该匹配表达式会引发 `Match_failure` 异常。我们还没有讨论过 OCaml 中的异常，但你在其他语言中一定对异常并不陌生。我们会在本章末尾（介绍完 OCaml 的其他一些内置数据结构之后）回到异常这个话题。

* 否则，令 `pi` 为第一个匹配成功的模式，令 $b$ 为将 `v` 与 `pi` 匹配所产生的变量绑定。

* 将绑定 $b$ 替换到 `ei` 中，产生新表达式 `e'`。

* 将 `e'` 求值为值 `v'`。

* 整个匹配表达式的结果就是 `v'`。

例如，下面展示如何求值这个匹配表达式：
```{code-cell} ocaml
match 1 :: [] with
| [] -> false
| h :: t -> h = 1 && t = []
```

* `1 :: []` 已经是一个值。

* `[]` 与 ``1 :: []`` 不匹配。

* `h :: t` 确实匹配 `1 :: []` 并生成变量绑定
{`h->1`,`t->[]`}，因为：

  - `h` 匹配 `1` 并生成变量绑定 `h->1`。

  - `t` 匹配 `[]` 并生成变量绑定 `t->[]`。

* 将 {`h->1`,`t->[]`} 替换为 `h = 1 && t = []` 内
生成一个新表达式 `1 = 1 && [] = []`。

* 求值 `1 = 1 && [] = []` 会产生值 `true`。我们省略了
此处说明该事实的理由，但它是根据其他求值规则得出的
  用于内置运算符和函数应用程序。

* 所以整个匹配表达式的结果是`true`。

**静态语义。**

* 如果 `e : ta`，且对所有 `i` 都有 `pi : ta` 和 `ei : tb`，那么 `(match e with p1 -> e1 | ... | pn -> en) : tb`。

这条规则依赖于判断模式是否具有特定类型的能力。和往常一样，类型推断在这里发挥作用。OCaml 编译器会推断出模式中所有模式变量和通配符的类型。列表模式与列表表达式遵循相同的类型检查规则。

**额外的静态检查。**

{{ video_embed | replace("%%VID%%", "aLQJpk9vXD4")}}

除了类型检查规则之外，编译器还会对每个匹配表达式执行另外两项检查。

第一项是**穷尽性检查**（exhaustiveness）：编译器会检查是否有足够多的模式，以保证无论表达式 `e` 在运行时的值是什么，至少有一个模式能匹配。这确保程序员没有遗漏任何分支。例如，下面的函数会导致编译器发出警告：

```{code-cell} ocaml
let head lst = match lst with h :: _ -> h
```

通过向程序员发出警告，编译器帮助程序员防范运行时可能出现的 `Match_failure` 异常。

```{note}
抱歉，上面这个单元格的输出在 HTML 中被分割成了多行。这是用于构建本书的框架 [JupyterBook 的一个已知 issue][issue]。

[issue]: https://github.com/executablebooks/jupyter-book/issues/973
```

第二项是**无用分支检查**（unused branch）：编译器会检查是否有任何分支因前面的分支总能匹配成功而永远不会被匹配到。例如，下面的函数会导致编译器发出警告：

```{code-cell} ocaml
let rec sum lst =
  match lst with
  | h :: t -> h + sum t
  | [ h ] -> h
  | [] -> 0
```

第二个分支不会被使用，因为第一个分支能匹配第二个分支所能匹配的任何值。

无用匹配分支通常意味着程序员写出的代码与其本意不符。因此，编译器通过发出警告来帮助程序员发现代码中的潜在错误。

下面是一个最常见的导致"无用匹配分支"警告的错误。理解这个例子也能检验你是否真正掌握了匹配表达式的动态语义：

```{code-cell} ocaml
let length_is lst n =
  match List.length lst with
  | n -> true
  | _ -> false
```

程序员原本想表达：如果 `lst` 的长度等于 `n`，则该函数返回 `true`，否则返回 `false`。但实际上，这个函数*总是*返回 `true`。为什么？因为模式变量 `n` 与函数参数 `n` 是不同的东西。假设 `lst` 的长度为 5，那么模式匹配变为：`match 5 with n -> true | _ -> false`。`n` 是否匹配 5？是的，根据前面的规则：变量模式匹配任何值，并产生绑定 `n->5`。然后求值会把这个绑定应用到 `true` 中——也就是用 5 替换 `true` 中所有出现的 `n`。由于 `true` 中根本没有 `n`，求值完成，结果就是 `true`。

程序员真正想写的是：
```{code-cell} ocaml
let length_is lst n =
  match List.length lst with
  | m -> m = n
```

或者更简洁地：

```{code-cell} ocaml
let length_is lst n =
  List.length lst = n
```

## 深度模式匹配

模式可以嵌套。这样可以让代码深入到列表的内部结构。例如：

* `_ :: []` 匹配所有恰好包含一个元素的列表

* `_ :: _` 匹配所有至少包含一个元素的列表

* `_ :: _ :: []` 匹配所有恰好包含两个元素的列表

* `_ :: _ :: _ :: _` 匹配所有至少包含三个元素的列表

## 即时匹配

{{ video_embed | replace("%%VID%%", "VgVP8Tin6yY")}}

当函数体一上来就直接对最后一个参数做模式匹配时，有一种很好的语法糖可以省去多余的代码。举个例子，与其这样写：
```{code-cell} ocaml
let rec sum lst =
  match lst with
  | [] -> 0
  | h :: t -> h + sum t
```
不如这样写：
```{code-cell} ocaml
let rec sum = function
  | [] -> 0
  | h :: t -> h + sum t
```
`function` 是一个关键字。注意我们省去了包含 `match` 的那一行，以及那个除了出现在那一行之外没在其他地方用过的参数名。但此时，为函数编写规范注释来记录参数的含义就尤为重要，因为代码不再为参数提供有意义的描述性名称。

## OCamldoc 与列表语法

OCamldoc 是一个类似于 Javadoc 的文档生成器。它从源代码中提取注释，并生成 HTML 等输出格式。`List` 模块的[标准库网页文档][std-web]就是由该模块的[标准库源码][std-src]中嵌入的 OCamldoc 注释生成的。

```{warning}
OCamldoc 中有一个使用方括号的语法约定，很容易与列表混淆。

在 OCamldoc 注释中，源代码用方括号括起来。被括起来的代码在输出的 HTML 中会以等宽字体呈现，并带有语法高亮。这里的方括号并不表示列表。
```

例如，下面是标准库源码中 `List.hd` 的注释：
```ocaml
(** Return the first element of the given list. Raise
   [Failure "hd"] if the list is empty. *)
```
`[Failure "hd"]` 并不表示一个包含异常 `Failure "hd"` 的列表，而是表示将表达式 `Failure "hd"` 以源代码格式排版，如[这里][std-web]所示。

当你想在文档中讨论列表时，这种歧义会变得特别让人困惑。例如，我们可以这样重写上面的注释：
```ocaml
(** [hd lst] returns the first element of [lst].
    Raises [Failure "hd"] if [lst = []]. *)
```
在 `[lst = []]` 中，外层方括号表示注释中的源代码排版，而内层方括号才是空列表。

[std-web]: https://ocaml.org/api/List.html
[std-src]: https://github.com/ocaml/ocaml/blob/trunk/stdlib/list.mli

## 列表推导式

一些语言（包括 Python 和 Haskell）提供了一种称为*推导式*（comprehension）的语法，让我们可以像数学中的集合推导式那样来书写列表。推导式最早的例子似乎来自 1977 年设计的函数式语言 NPL。

OCaml 没有内置推导式语法支持。虽然有过一些扩展，但似乎已不再被维护。推导式能完成的主要任务（过滤掉部分元素、转换其他元素）实际上已经被*高阶编程*（我们将在后续章节学习）以及管道运算符（我们已经学过）很好地覆盖了。因此，推导式提供的额外语法从来不是必需的。

## 尾递归

回想一下，如果一个函数递归地调用自身，且递归调用返回之后不再执行任何计算，而是立即将递归调用的值返回给调用者，那么这个函数就是*尾递归*的。考虑下面两个对列表求和的实现，`sum` 和 `sum_tr`：

```{code-cell} ocaml
let rec sum (l : int list) : int =
  match l with
  | [] -> 0
  | x :: xs -> x + (sum xs)

let rec sum_plus_acc (acc : int) (l : int list) : int =
  match l with
  | [] -> acc
  | x :: xs -> sum_plus_acc (acc + x) xs

let sum_tr : int list -> int =
  sum_plus_acc 0
```

观察 `sum` 和 `sum_tr` 函数之间的区别：在非尾递归的 `sum` 中，递归调用返回后，我们还要把 `x` 加到返回值上。而在尾递归的 `sum_tr` 中（或者更准确地说，在 `sum_plus_acc` 中），递归调用返回后，我们立即原样返回其值，不做任何进一步计算。

如果你要在非常长的列表上编写函数，尾递归对性能就很重要。因此，当你可以在尾递归和非尾递归之间做选择时，对于长列表，使用尾递归函数往往能获得更好的空间效率。`List` 模块的文档也因此注明了哪些函数是尾递归的，哪些不是。

但这并不意味着尾递归实现一定更好。例如，尾递归函数可能更难阅读（想想 `sum_plus_acc`）。此外，某些情况下要将函数实现为尾递归，需要对列表进行预处理或后处理来反转列表。在中小型列表上，反转列表带来的开销（包括时间开销和额外内存开销）反而可能使尾递归版本的时间效率更低。至于这里的"小"和"大"如何界定，很难给出确切答案，可以参见 [`List` 模块的标准库文档][list]。

[list]: https://ocaml.org/api/List.html

这是一个很有用的尾递归函数，用来生成一个长列表：

```{code-cell} ocaml
(** [from i j l] is the list containing the integers from [i] to [j],
    inclusive, followed by the list [l].
    Example:  [from 1 3 [0] = [1; 2; 3; 0]] *)
let rec from i j l = if i > j then l else from i (j - 1) (j :: l)

(** [i -- j] is the list containing the integers from [i] to [j], inclusive. *)
let ( -- ) i j = from i j []

let long_list = 0 -- 1_000_000
```

值得仔细研究一下 `--` 的定义，确保自己理解 (i) 它如何工作，以及 (ii) 为什么它是尾递归的。

将来你可能还需要再次创建类似的列表。除了需要记住这段定义在哪里并复制到代码中之外，也可以用内置库函数更简单地实现同样的效果：

```{code-cell} ocaml
List.init 1_000_000 Fun.id
```

表达式 `List.init len f` 会创建列表 `[f 0; f 1; ...; f (len - 1)]`，且当 `len` 大于 10,000 时会采用尾递归方式。函数 `Fun.id` 就是恒等函数 `fun x -> x`。
