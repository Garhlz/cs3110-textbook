2.7. 调试#

当其他一切办法都失效时，调试才是最后的手段。先退一步，想一想那些发生在调试之前的事情。

2.7.1. 对抗 Bug 的防线#

根据 Rob Miller 的说法，对抗 bug 有四道防线：

  1. 第一道防线，是让 bug 根本不可能出现。

    如果你选择使用那些能够保证*内存安全和类型安全的语言来编程，那么整类整类的 bug 都可以被消除。所谓内存安全，是指除非通过对应该内存区域有效的指针*（或引用），否则程序不能访问那块内存；所谓类型安全，是指一个值不能以与其类型不一致的方式被使用。举例来说，OCaml 的类型系统能防止缓冲区溢出以及一些毫无意义的操作（例如把布尔值和浮点数相加），而 C 的类型系统则做不到这一点。

  2. 第二道防线，是使用能够发现 bug 的工具。

    有一些自动化的源代码分析工具，例如 FindBugs，它能发现 Java 程序中许多常见类型的 bug；还有 SLAM，它被用来发现设备驱动程序中的 bug。计算机科学中有一个分支叫做形式化方法（formal methods），研究的是如何用数学手段来规定和验证程序，也就是如何证明程序没有 bug。我们会在这门课后面学习验证相关内容。

    代码评审、结对编程这类社会性方法（social methods）也是发现 bug 的有用工具。IBM 在 20 世纪 70 到 90 年代的一些研究表明，代码评审可能非常有效。其中一项研究（Jones, 1991）显示，代码检查找出了 65% 的已知编码错误和 25% 的已知文档错误，而测试只找出了 20% 的编码错误，对文档错误则一个也没发现。

  3. 第三道防线，是让 bug 立刻暴露出来。

    bug 越早显现出来，就越容易诊断和修复。反过来，如果程序在 bug 出现之后还继续往下执行，那么后续的计算反而可能掩盖真正出错的位置。源代码中的断言（assertion）可以让程序“尽早失败”“大声失败”，使 bug 立刻显现出来，从而让程序员明确知道应当回到源代码的哪里去排查。

  4. 第四道防线，是充分测试。

    你怎么知道一段代码是否包含某个特定 bug？写出能够暴露该 bug 的测试，然后确认你的代码不会在这些测试上失败。对于比较小的代码单元，例如单个函数或模块，单元测试尤其应该和开发同步进行。这些测试还应该自动运行，这样一旦你改坏了代码，就能尽快发现。（说到底，这其实又回到了第三道防线。）

当前面这些防线全都失守之后，程序员才不得不诉诸调试。

2.7.2. 如何调试#

假设你已经发现了一个 bug。接下来该怎么办？

  1. 把 bug 提炼成一个小型测试用例。 调试很费力，而测试用例越小，你就越可能把注意力集中在 bug 藏身的那段代码上。花时间做这一步提炼，往往反而能节省时间，因为你不必反复重读大量代码。在你拿到一个足够小的测试用例之前，不要继续调试。

  2. 采用科学方法。 针对 bug 为什么会发生，提出一个假设。你甚至可以像在化学实验室里那样，把这个假设写在笔记本上，既帮助自己理清思路，也方便记录哪些假设已经考虑过。接下来，设计一个实验来验证或否定这个假设。运行实验并记录结果。根据学到的新信息，重新调整你的假设。就这样持续下去，直到你以理性、科学的方式确定 bug 的根本原因。

  3. 修复 bug。 修复可能只是改正一个简单的笔误；也可能暴露出某个设计缺陷，迫使你做较大的改动。还要考虑是否需要把这个修复应用到代码库中的其他地方，例如：这会不会其实是一次复制粘贴导致的错误？如果是，你是否需要重构代码？

  4. 把这个小测试用例永久加入测试套件。 你当然不希望这个 bug 再次悄悄回到代码库里。所以，应该把刚才提炼出来的小测试用例保留下来，作为单元测试的一部分。这样一来，你以后每次修改代码时，都会自动防范同一个 bug 再度出现。反复运行从历史 bug 中提炼出的测试，就是回归测试（regression testing）的一部分。

2.7.3. 在 OCaml 中调试#

下面是一些在 OCaml 中调试的技巧，前提是你真的已经不得不走到这一步了。

  • 打印语句。 插入打印语句来确认某个变量的值。假设你想知道下面这个函数中 x 的值：

    let inc x = x + 1

    那么只要加上一行打印它的代码即可：

    let inc x =
  let () = print_int x in
  x + 1

  • 函数跟踪。 假设你想看一个函数递归调用与返回的轨迹（trace），可以使用 #trace 指令：

    # let rec fib x = if x <= 1 then 1 else fib (x - 1) + fib (x - 2);;
# #trace fib;;

    如果你对 fib 2 求值，就会看到如下输出：

    fib <-- 2
fib <-- 0
fib --> 1
fib <-- 1
fib --> 1
fib --> 2

    若要停止跟踪，可以使用 #untrace 指令。

  • 调试器。 OCaml 自带一个调试工具 ocamldebug。你可以在 OCaml 官网找到它的 教程。除非你使用 Emacs 作为编辑器，否则你大概率会觉得这个工具还不如直接插入打印语句来得顺手。

2.7.4. 防御性编程#

正如我们前面在调试部分提到的那样，对抗 bug 的一种方式，是让任何 bug（或错误）都能立刻显现出来。这和前置条件的思想密切相关。

考虑 random_int 的下面这条规格说明：

(** [random_int bound] is a random integer between 0 (inclusive)
    and [bound] (exclusive).  Requires: [bound] is greater than 0
    and less than 2^30. *)

如果 random_int 的调用者传入了一个违反 Requires 子句的 bound 值，例如 -1，那么 random_int 的实现理论上就可以“为所欲为”。一旦调用者违背了前置条件，就不能再对函数行为作任何保证。

但对 random_int 来说，最有帮助的做法其实是立即暴露“前置条件被破坏了”这一事实。毕竟，调用者大概率并不是故意要违反它。

因此，random_int 的实现者最好检查前置条件是否被违反；如果违反了，就抛出异常。下面是三种这种防御性编程的写法：

(* possibility 1 *)
let random_int bound =
  assert (bound > 0 && bound < 1 lsl 30);
  (* proceed with the implementation of the function *)

(* possibility 2 *)
let random_int bound =
  if not (bound > 0 && bound < 1 lsl 30)
  then invalid_arg "bound";
  (* proceed with the implementation of the function *)

(* possibility 3 *)
let random_int bound =
  if not (bound > 0 && bound < 1 lsl 30)
  then failwith "bound";
  (* proceed with the implementation of the function *)

第二种写法对调用者来说大概最有信息量，因为它使用内置函数 invalid_arg 抛出了一个名字很明确的异常 Invalid_argument。事实上，这正是标准库中这个函数的实现方式。

第一种写法更适合你在调试自己的代码时使用，而不是把断言失败直接暴露给调用者。

第三种写法和第二种的区别，只在于所抛出的异常名字不同：它抛出的是 Failure。当某个前置条件不止涉及一个无效参数时，这种写法有时会更合适。

在这个例子里，检查前置条件的计算成本很低。但在别的场景中，前置条件检查可能代价高昂，因此函数实现者也可能选择不检查，或者只检查一个成本较低的近似条件。

有时程序员会过度担心防御性编程太昂贵，不管是实现这些检查本身所花的时间，还是运行时做断言检查所增加的成本。这种担忧往往并不成立。社会为了修复软件缺陷所付出的时间和金钱，已经足以说明：哪怕程序因此运行得稍微慢一点，我们也完全承担得起。

最后，实现者甚至可能选择彻底取消前置条件，转而把它改写成后置条件：

(** [random_int bound] is a random integer between 0 (inclusive)
    and [bound] (exclusive).  Raises: [Invalid_argument "bound"]
    unless [bound] is greater than 0 and less than 2^30. *)

这样一来，当 bound 太大或太小时，random_int 就不再是“想做什么都行”，而是必须抛出异常。对这个函数来说，这大概是更好的选择。

在这门课里，我们不会强制你采用防御性编程。但如果你够老练，你大概会主动开始这样做，或者继续这样做。你在编写这些防线时投入的那一点点时间，往往会在后面的调试中帮你节省数小时，让你成为更高效的程序员。
